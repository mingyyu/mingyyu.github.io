One recipe

Split, wish, join.

Every sort on this page is built the same way.

  1. Split the list into something smaller.
  2. Wish. Sort the smaller pieces by calling the function you’re in the middle of writing, and assume it works.
  3. Join the sorted pieces into one sorted list.

Step two is what CS1101S calls wishful thinking. You don’t trace the recursive call. You assume it returns the right answer and ask only what’s left for you to do. That’s easy to say and hard to believe, because you never get to watch it happen. Here you can: every dashed box on this page is a call you’re asked to trust, and if you keep scrolling, it opens.

Where the work goes

The four sorts differ in just two choices. Do you split off one element, or cut the list in two? And do the comparisons happen while splitting, on the way down, or while joining, on the way back up?

Where comparisons happen Split off one Cut in two
↑ Compare on the way back up Easy split, hard join Insertion sort Split with head and tail, join with insert. Θ(n²) Merge sort Split with take and drop, join with merge. Θ(n log n)
↓ Compare on the way down Hard split, easy join Selection sort Split with smallest and remove, join with pair. Θ(n²) Quicksort Split with filter around a pivot, join with append. Θ(n log n), if the pivots are kind

Insertion sort

Split off one, compare on the way back up.

The version you’ve probably written already: take the head off, sort the tail by wishful thinking, then insert the head where it belongs.

Start with one call on the whole list. Insertion sort’s split is as cheap as a split gets: head(xs) is 5, and tail(xs) is the other seven.

Here is the wish. Hand the tail to insertion_sort and assume it comes back sorted. You don’t trace that call, and you don’t need to know how it works yet. The box stays shut.

Say the wish comes true: seven tiles, in order. All that’s left for this call is to fit the 5 in.

insert walks along the sorted list. Each tile smaller than 5 stays in front, pair(head(xs), …), and the 5 carries on into the tail. At 6 it stops, because x <= head(xs), and 5 goes in front of everything left.

That’s the whole algorithm: one insert, plus trust in a shorter list.

Now open the box. The call you trusted does exactly the same thing to a list one shorter: set the head aside, wish on the tail. Each row down is one call deeper, and each row has its own box.

Eight calls down, the list runs out and the base case answers straight away: None is already sorted.

Look at the grey diagonal. Every call has set a number aside and is waiting to insert it. Nothing is sorted yet; all of the work is still owed.

That staircase is also the memory bill. The computer has to hold every pending insert at once, one per element: n deferred operations, so Θ(n) space.

Now the wishes come true, from the bottom up. The deepest call inserts 6 into an empty list. The one above inserts 3 into llist(6), then 8 goes into llist(3, 6).

So this insertion sort builds its answer from the back of the input.

Each insert walks only as far as it has to. The 1 goes to the front after a single comparison. The 7 has to pass four tiles, and it takes five comparisons to find its spot before 8.

Back at the top, the first call finally inserts 5 into the sorted seven. It’s the same move you trusted at the start, and this time you watched the wish come true.

Each dot is one comparison. The call at depth k inserts into a list of 7 − k tiles, so it can make at most that many (the hollow dots).

Worst case, a reversed list: 0 + 1 + ⋯ + 7 = 28, a full triangle, Θ(n²). Best case, a list that’s already sorted: every insert stops at its first comparison, n − 1 in all, Θ(n). This list took 19.

def insert(x, xs):
    if is_none(xs):
        return llist(x)
    elif x <= head(xs):
        return pair(x, xs)
    else:
        return pair(head(xs), insert(x, tail(xs)))
 
def insertion_sort(xs):
    if is_none(xs):
        return xs
    else:
        return insert(head(xs), insertion_sort(tail(xs)))

Selection sort

Split off one, compare on the way down.

Same shape, but the work moves to before the wish: find the smallest, take it out, and sort what’s left.

Selection sort does its thinking first. smallest reduces the list, keeping the smaller of each pair as it goes. It has to look at every tile, because the smallest could be the last one. Seven comparisons to find the 1.

Take the 1 out with remove and hand the other seven to the wish. The box stays shut.

Trust it: the seven come back sorted.

So the join is a single pair: 1 in front of the rest, with nothing to compare. The hard part happened before the wish.

Open the box and it’s the insertion sort staircase again, but mirrored. Each call scans what’s left, sets the smallest aside and wishes on the rest. The comparing happens on the way down.

Each scan is one shorter than the last: seven comparisons, then six, then five.

By the bottom, the grey diagonal already reads 1 to 8. The order is settled, but every call is still waiting on the pair that puts its number in front. Eight pending operations again: Θ(n) space.

The way back up is quick. Each call pairs its number onto whatever came back from below. No comparisons, one step a row.

The dots make a perfect triangle: 7 + 6 + ⋯ + 1 = 28. It would be exactly the same for any list of eight, because smallest can’t stop early. Selection sort is Θ(n²) in every case.

Insertion sort’s worst case is selection sort’s every case.

def smallest(xs):
    return reduce(lambda x, y: (x if x < y else y),
                  head(xs),
                  tail(xs))
 
def selection_sort(xs):
    if is_none(xs):
        return xs
    else:
        x = smallest(xs)
        return pair(x, selection_sort(remove(x, xs)))

Merge sort

Cut in two, compare on the way back up.

Cut the list in half instead of peeling off one element. That means two wishes, and a join that does real work.

Merge sort splits the list down the middle: take the first middle(length(xs)) tiles, and drop them to get the rest.

Two wishes this time. Assume merge_sort sorts each half, and don’t look inside.

Both halves come back sorted. Now, how do you turn two sorted lists into one?

Zip them. The smallest tile overall must be at the front of one half or the other, so compare the two fronts and take the smaller. Repeat. When one side runs out, the rest of the other goes on as it is.

Seven comparisons for eight tiles.

Now open the boxes, and see what most merge sort diagrams get wrong. The two halves are not sorted side by side. Python evaluates the first argument to merge completely before it starts on the second, so the left half goes all the way down first.

The right half waits in the top row, faded. It hasn’t even been cut off yet.

At the bottom, a single tile is already sorted, so the base case hands it straight back. The first merge anywhere is 5 and 2 becoming llist(2, 5).

One level up, the other quarter goes down, comes back as llist(4, 7), and the two merge. The left half of the whole list is done: 2 4 5 7.

Only now does the right half start, and it repeats the pattern exactly.

Last comes the merge you trusted at the very beginning.

Read the ledger by row. Each level merges all eight tiles between its calls, and every comparison places one tile, so a level costs fewer than n comparisons. Halving 8 reaches 1 after log2 8 = 3 levels.

n per level times log n levels: Θ(n log n). The work is a short, wide rectangle instead of a triangle, whatever order the input came in.

Space is subtler. The dashed boxes are the calls waiting at any moment, and there are never more than log n of them. But merge is a recursive process too: the final merge leaves up to n pairs pending. Written this way, merge sort still needs Θ(n) space.

def merge_sort(xs):
    if is_none(xs) or is_none(tail(xs)):
        return xs
    else:
        mid = middle(length(xs))
        return merge(merge_sort(take(xs, mid)),
                     merge_sort(drop(xs, mid)))
 
def merge(xs, ys):
    if is_none(xs):
        return ys
    elif is_none(ys):
        return xs
    else:
        x = head(xs)
        y = head(ys)
        if x < y:
            return pair(x, merge(tail(xs), ys))
        else:
            return pair(y, merge(xs, tail(ys)))

Quicksort

Cut in two, compare on the way down.

This one isn’t among the three from the course, but it fills the last square of the map. It’s merge sort turned inside out: the split does all the comparing, and the join does none.

Pick a pivot. The simplest choice is the head: 5.

The first filter walks the tail and sends everything smaller than 5 down to the left.

The second filter walks the whole tail again to collect everything else. That’s two passes where one would do, but the order of growth won’t notice.

Now look where the 5 lands. Everything to its left is smaller and everything to its right is larger, so it’s already in its final place.

Wish both sides sorted.

The join is append, and it compares nothing. The split already put every tile on the right side of the pivot, so the pieces just stack back together.

Open the boxes. Each side picks its own pivot and splits again. The pieces aren’t halves; they’re whatever size the pivot makes them: 4 and 3 here, then 1 and 2.

Once a pivot turns green, it never moves again.

On this list the splits come out fairly even, the deepest call is only three levels down, and the whole sort costs 26 comparisons: two for each tile at each level it passes through.

Now give it a list that’s already sorted. The pivot is always the smallest thing left, so every other tile goes right and the left side is always empty.

The tree turns into a staircase eight calls deep. It’s selection sort in disguise, comparing twice as often.

On the way back up, each append just stacks the pieces.

Even splits give about log n levels of n work each: Θ(n log n). A pivot that always lands at one end gives n levels: Θ(n²), here 56 comparisons against 26.

With the head as pivot, the input you’d expect to be easiest is the worst possible one. That’s why real quicksorts pick their pivot at random.

def quicksort(xs):
    if is_none(xs):
        return xs
    else:
        p = head(xs)
        smaller = filter(lambda x: x < p, tail(xs))
        larger = filter(lambda x: x >= p, tail(xs))
        return append(quicksort(smaller),
                      pair(p, quicksort(larger)))

What it costs

Counted in comparisons, the one step every sort here shares.

Time first. The figures below run all four sorts on a list of 32 and draw the work the way the ledgers above did: one row per level of recursion, one square per comparison. The area is the time. Change the order of the input and watch the shapes.

Input

Space

Space in the CS1101S sense means how many deferred operations the computer has to hold at the deepest point. Written this way, all four sorts need Θ(n), for different reasons.

  • Insertion sort holds one pending insert per element: the grey diagonal.
  • Selection sort holds one pending pair per element: the same diagonal, already in order.
  • Merge sort’s own calls are only log n deep, but merge is a recursive process, and the last merge leaves up to n pairs waiting.
  • Quicksort holds the pending appends along one path of calls. On an already-sorted list that path is n long.

Can anything beat n log n?

Not by comparing.

Three numbers can arrive in 3! = 6 different orders, and a sort has to tell all six apart. Each comparison has two outcomes, so k comparisons can tell apart at most 2k orders. Six orders need at least three comparisons, and here they are:

For n numbers you need 2k ≥ n!, so k ≥ log2(n!), and log2(n!) grows like n log2 n. No sort that works by comparing can do better in the worst case. Merge sort is already there.

Faster sorts get there by not comparing at all. If you know your numbers are small whole numbers below k, you can count how many of each there are and write them back out in order. That’s counting sort, Θ(n + k), and it only works because it knows something about the numbers.
