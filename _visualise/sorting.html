One recipe

Split, wish, join.

All four sorts on this page follow the exact same pattern.

  1. Split the list into smaller pieces.
  2. Wish. Sort those pieces by calling the function you’re still writing, trusting that it works.
  3. Join the sorted pieces back into a single sorted list.

CS1101S calls step two wishful thinking. Instead of tracing the recursive call, you trust it to hand back a sorted list and focus only on the step left in front of you. That’s easy to say on paper, and much easier to believe once you watch it run. Every dashed box below is a recursive call you take on faith; keep scrolling to open it up.

Where the work goes

Two decisions separate the four sorts. First, do you peel off a single element, or halve the list? Second, do you compare elements on the way down while splitting, or on the way back up while joining?

Where comparisons happen Split off one Cut in two
↑ Compare on the way back up Easy split, hard join Insertion sort Split with head and tail, join with insert. Θ(n²) Merge sort Split with take and drop, join with merge. Θ(n log n)
↓ Compare on the way down Hard split, easy join Selection sort Split with smallest and remove, join with pair. Θ(n²) Quicksort Split with filter around a pivot, join with append. Θ(n log n), if the pivots are kind

Insertion sort

Peel off one, compare on the way back up.

This is usually the first recursive sort you write: pull off the head, sort the tail by wishful thinking, and slide the head into place.

We start with a single call on all eight numbers. Splitting here takes almost no work: head(xs) grabs 5, leaving the remaining seven in tail(xs).

Now make the wish. Pass the seven-element tail to insertion_sort and trust that it returns in order. We don’t look inside that call yet; its box stays closed.

Once the wish returns those seven tiles in order, this call only has one job left: slot the 5 into the right spot.

insert steps through the sorted seven from left to right. Any tile smaller than 5 stays ahead of it via pair(head(xs), …) while 5 keeps moving into the tail. As soon as it hits 6, x <= head(xs) holds, so 5 drops in right before 6 and the rest of the list.

That’s the entire sort: trust the recursive call on a shorter list, then run a single insert.

Now let’s look inside the dashed box. That trusted call runs the exact same steps on seven elements: hold the head aside, wish on the remaining six. Every row down goes one call deeper and opens another box.

After eight levels of splitting, the list is empty and hits the base case: None is trivially sorted.

Notice the grey diagonal. Each call is holding one number aside, waiting for the call below it to finish before it can insert. No comparisons have happened yet; all the real work is waiting on the return trip.

That diagonal also shows the memory cost. Because every call is waiting on the one below it, the machine has to keep n pending insert calls alive at once, taking Θ(n) space.

Now the calls resolve from the bottom up. The deepest level puts 6 into the empty list. One row up, 3 slips in front of llist(6), and the next row places 8 into llist(3, 6).

Because the deepest calls finish first, recursive insertion sort actually assembles the sorted list starting from the back of the input.

Each insert stops as soon as it finds its spot. Tile 1 lands at the front after just one comparison, while 7 steps past four smaller numbers and uses five comparisons before settling in front of 8.

At last we reach the top row again, where the original call slots 5 into the seven sorted tiles. It’s the exact step we assumed would work at the beginning, only now we’ve seen every level beneath it.

The dots on the right tally comparisons. A call at depth k inserts into a sorted list of length 7 − k, so it does at most that many comparisons (shown as hollow dots).

On a reverse-sorted list, every insert walks all the way to the end: 0 + 1 + ⋯ + 7 = 28 comparisons, filling the whole triangle for Θ(n²) time. On an already-sorted list, each insert finishes on its first check, taking just n − 1 comparisons, or Θ(n). Our eight numbers took 19.

def insert(x, xs):
    if is_none(xs):
        return llist(x)
    elif x <= head(xs):
        return pair(x, xs)
    else:
        return pair(head(xs), insert(x, tail(xs)))
 
def insertion_sort(xs):
    if is_none(xs):
        return xs
    else:
        return insert(head(xs), insertion_sort(tail(xs)))

Selection sort

Peel off one, compare on the way down.

The call tree has the same shape as insertion sort, except the comparisons happen before the recursive call: scan for the smallest number, pull it out, and sort the rest.

Selection sort pays its comparison cost up front. smallest walks the entire list, keeping the smaller value at each step. Because the minimum could be hiding at the very end, it checks every tile, taking seven comparisons to find 1.

Pull 1 out with remove and pass the remaining seven tiles into the recursive wish. Leave the box closed for now.

Take the wish on trust: those seven tiles return in sorted order.

Joining is then effortless. A single pair attaches 1 to the front of the sorted seven without a single comparison, since all the work was done before the wish.

Open the dashed box and you get the same staircase as insertion sort, only flipped. Every call searches the remaining tiles, pulls out the smallest, and wishes on the rest. All the comparisons happen on the way down.

Each pass scans one fewer tile than the row above it: seven comparisons, then six, then five.

By the time we reach the bottom, the grey diagonal already runs from 1 to 8 in order. Even though the positions are decided, all eight calls are still waiting to run pair on the way back up, which still costs Θ(n) space.

Unwinding the calls is instant. Each row simply pairs its saved minimum onto the front of the list returned from below, with zero comparisons.

The comparison ledger forms a solid triangle every time: 7 + 6 + ⋯ + 1 = 28. Because smallest always scans to the end of the list, the input order never saves a single step. Selection sort takes Θ(n²) in best, average, and worst cases alike.

What insertion sort suffers only on a reversed list, selection sort pays on every list.

def smallest(xs):
    return reduce(lambda x, y: (x if x < y else y),
                  head(xs),
                  tail(xs))
 
def selection_sort(xs):
    if is_none(xs):
        return xs
    else:
        x = smallest(xs)
        return pair(x, selection_sort(remove(x, xs)))

Merge sort

Halve the list, compare on the way back up.

Instead of shaving off one element at a time, slice the list down the middle. We make two wishes per call, and do the real work when combining the sorted halves.

Merge sort divides the list into two equal halves: take grabs the first middle(length(xs)) tiles, and drop leaves the second half.

Now we make two wishes side by side, trusting merge_sort to hand back each four-tile half in order without peeking inside.

Once both four-tile halves come back sorted, we only need a fast way to weave two sorted lists into one.

We zip them together. Since both halves are already in order, the smallest remaining number has to sit at the front of one of them. Compare the two fronts, take the smaller one, and repeat until one half is empty, then tack on whatever is left of the other.

Merging all eight tiles here takes seven comparisons.

Opening the boxes reveals something static textbook diagrams usually hide: the two halves don’t actually run in parallel. Python finishes evaluating the first argument to merge before touching the second, so execution dives all the way down the left branch first.

Meanwhile, the right half sits waiting at the top, dimmed out before it is even split.

At the bottom of the left branch, a one-element list is already sorted and returns immediately. The very first merge on the page combines 5 and 2 into llist(2, 5).

Stepping back up one level, the second pair splits, returns as llist(4, 7), and merges with the first pair to finish the entire left half: 2 4 5 7.

With the left half complete, execution finally starts down the right half and follows the exact same sequence.

Everything finishes with the top-level merge we took on faith at the start.

Look at the comparison ledger row by row. Across any single level of the tree, the calls together merge all eight tiles, and each comparison places one tile into its merged list, so a level costs fewer than n comparisons. Halving eight elements reaches single tiles in log2 8 = 3 levels.

At most n comparisons across log n levels gives Θ(n log n) time. Instead of a deep triangle, the ledger forms a shallow rectangle regardless of how the input was ordered.

Memory is a bit subtler. Only log n dashed recursive calls are ever active at once, because the left branch finishes before the right branch starts. However, a recursive merge stacks up to n pending pair calls during the final combine, so this implementation still uses Θ(n) space.

def merge_sort(xs):
    if is_none(xs) or is_none(tail(xs)):
        return xs
    else:
        mid = middle(length(xs))
        return merge(merge_sort(take(xs, mid)),
                     merge_sort(drop(xs, mid)))
 
def merge(xs, ys):
    if is_none(xs):
        return ys
    elif is_none(ys):
        return xs
    else:
        x = head(xs)
        y = head(ys)
        if x < y:
            return pair(x, merge(tail(xs), ys))
        else:
            return pair(y, merge(xs, tail(ys)))

Quicksort

Halve the list, compare on the way down.

CS1101S doesn’t cover quicksort alongside the first three, but it completes our two-by-two grid. Think of it as merge sort flipped upside down: all comparisons happen while splitting, so joining is free.

First, choose a pivot element. Taking the head of the list gives us 5.

One call to filter scans the tail and gathers every tile smaller than 5 into the left group.

A second filter scans the tail again to gather everything at least as large as 5. Walking the tail twice does extra work, though it leaves the asymptotic order of growth unchanged.

Notice where 5 ends up. Because every smaller number went left and every larger number went right, the pivot is already sitting in its final sorted position.

Make two wishes to sort the left and right groups.

Joining uses append without a single comparison. Since partitioning already separated small from large around the pivot, we simply concatenate the sorted left group, the pivot, and the sorted right group.

Open the dashed boxes and each subgroup chooses its own pivot to partition again. Unlike merge sort, the split sizes depend entirely on the pivot: 4 and 3 on the first split, then 1 and 2 on the next.

Every time a pivot turns green, it is locked in place for the rest of the run.

Because our pivots happen to split this list fairly evenly, the tree goes only three levels deep and finishes in 26 comparisons (two passes over the remaining tail at each level).

Watch what happens if the input arrives already sorted. Because we always pick the head, every pivot is the smallest number left, sending all remaining tiles to the right and leaving the left branch empty.

The balanced tree collapses into an eight-level staircase. Quicksort degrades into selection sort, doing twice as many comparisons because of the two filter passes.

Returning up the chain still just runs append at each level.

Balanced pivots keep the tree to about log n levels with linear work per level, giving Θ(n log n). Pivots that hug the ends stretch the tree to n levels and Θ(n²) work: 56 comparisons here instead of 26.

Picking the first element as the pivot makes an already-sorted list the worst possible input. Production quicksorts avoid that trap by choosing a random pivot.

def quicksort(xs):
    if is_none(xs):
        return xs
    else:
        p = head(xs)
        smaller = filter(lambda x: x < p, tail(xs))
        larger = filter(lambda x: x >= p, tail(xs))
        return append(quicksort(smaller),
                      pair(p, quicksort(larger)))

Input

Space

In CS1101S, space complexity counts the maximum number of deferred operations waiting on the call stack at once. Under these pure functional implementations, all four algorithms use Θ(n) space, each for its own reason.

  • Insertion sort stacks up one deferred insert per element along its grey diagonal.
  • Selection sort stacks up one deferred pair per element along the same diagonal, even though the values are already chosen in order.
  • Merge sort keeps at most log n recursive sort calls open at once, but its recursive merge helper builds a chain of up to n waiting pair calls on the final pass.
  • Quicksort holds one deferred append per active level of recursion, which reaches n levels deep when given an already-sorted list.

Can anything beat n log n?

Not by comparing.

Three items can be arranged in 3! = 6 possible permutations, and a working sort has to distinguish all six. Because a single comparison branches only two ways, k comparisons can separate at most 2k permutations. Separating six outcomes therefore takes at least three comparisons, shown in the decision tree below:

Generalising to n elements requires 2k ≥ n!, meaning k ≥ log2(n!), which grows asymptotically as n log2 n. No comparison sort can beat that bound in the worst case, and merge sort already matches it.

Beating n log n means skipping element-to-element comparisons altogether. If your input consists of small integers bounded by k, you can simply tally how often each number appears and write them out in order. That algorithm is counting sort, running in Θ(n + k) time by exploiting the structure of the keys.

def bogosort(xs):
    while not is_sorted(xs):
        xs = shuffle(xs)
    return xs
